# KML 数据管理面板渲染与状态保持优化需求

状态：问题已复盘；v1.5.74 的首轮修复在真实浏览器中仍发现折叠/删除竞态，v1.5.75 已补齐按文件失效与隐藏布局处理，待 161 内测验收；分阶段动态渲染方案按本文路线排期

记录日期：2026-09-09

## 1. 文档目的

本文记录 KML 数据管理面板在点位、线段或面数量较多时的滚动状态丢失问题，并定义后续渲染架构优化方案。文档同时评估是否引入 MVVM、MVC 或主流前端框架，作为后续页面和组件开发的决策依据。

本问题不涉及 KML 数据格式、服务端接口或地图几何语义变更。优化必须保持 2D/3D、个人 KML、公共 KML、分享只读模式、点位显隐、线段编辑、拖拽整理、批量操作和媒体入口的一致行为。

## 2. 问题记录

### 2.1 用户表现

当一个 KML 文件包含较多点位或线段时，用户在该文件内部列表滚动到中间位置后执行以下操作，列表会回到顶部：

1. 点击点位或线段的显示/隐藏按钮。
2. 编辑点位名称、描述、图标或线段属性并保存。
3. 移动、复制、删除或排序要素后继续操作同一文件。
4. 在分享只读面板中切换文件或要素显隐。
5. 在 3D 页面执行同类操作。

用户被迫重新搜索刚才的点位，连续编辑成本随列表长度增加而放大。

### 2.2 复现条件

- 打开 KML 数据管理面板。
- 展开包含超过可视高度的 KML 文件，使 `.kml-features-list` 出现纵向滚动条。
- 将该内部列表滚动到非零位置（例如 `scrollTop >= 100`）。
- 点击任意点位/线段的显隐按钮，或编辑名称并保存。
- 观察同一 KML 文件内部列表的 `scrollTop` 被重置为 `0`。

### 2.3 根因证据

1. `src/styles.css` 中 `.kml-features-list` 设置了 `max-height: 200px` 和 `overflow-y: auto`，它才是点位/线段实际的滚动容器；外层 `.kml-panel-body` 不是唯一滚动容器。
2. 2D 管理面板 `src/map/kml.js`、2D 分享面板和 3D 管理面板通过 `#kml-files-list.innerHTML = ...` 生成整棵列表树。
3. 整段替换会销毁旧的 `.kml-features-list` 节点。新节点的 `scrollTop` 默认是 `0`，即使外层面板的 `scrollTop` 被恢复，内层列表仍然回到顶部。
4. 点位显隐、名称编辑保存和视口/弹窗异步刷新可能连续触发两次以上面板重绘；单次同步恢复不足以覆盖后续重绘。
5. v1.5.73 只保存了外层 `.kml-panel-body` 的数值位置，未保存内部列表，也未覆盖 2D 分享和 3D 分支，因此没有解决完整问题。

### 2.4 为什么现有代码使用 `innerHTML`

当前实现不是因为浏览器不能动态更新，而是历史上选择了“一次计算状态、一次生成模板”的简单边界：

- 权限、目录、文件显隐、展开状态、视口虚拟化、批量选择和错误状态都在同一处计算，整段模板可以避免局部更新遗漏字段。
- 面板使用容器级事件委托，替换子节点不会为每一行重复注册事件，代码量和监听器数量较小。
- 2D/3D 面板需要在文件详情加载、视口变化和账号同步后统一刷新，整段模板在功能早期更容易保持一致。

这个选择的代价是 DOM 身份状态被一并销毁，包括内部滚动位置、键盘焦点、文本选择、原生输入状态和部分辅助技术上下文。随着页面和组件增多，继续在业务代码中直接写 `innerHTML` 会使状态保持、局部更新和性能优化越来越难验证。

结论：短期不必为了一个 bug 立即引入大型框架；中期必须把模板生成与 DOM 更新隔离，并逐步采用稳定 ID 的 keyed 动态更新。

## 3. 已实施的短期修复（v1.5.74-v1.5.75）

### 3.1 行为

- 统一通过 `src/map/kml-panel-scroll.js` 捕获外层 `.kml-panel-body` 与全部 `.kml-features-list` 的 `scrollTop/scrollLeft`。
- 以 KML 文件稳定 ID（`data-kml-scroll-key`，兼容最近的 `data-kml-card-id`/`data-kml-id`）匹配重绘前后的内部列表，不依赖列表索引。
- 2D 个人面板、2D 分享面板和 3D 面板均使用统一替换入口。
- 替换后立即恢复，并在后续两帧再次恢复，覆盖 `content-visibility`、布局计算和 popup/视口异步二次重绘。
- 设置 `overflow-anchor: none`，避免浏览器自动滚动锚点与应用恢复逻辑互相覆盖。
- 恢复逻辑带容器级代次校验，旧的异步恢复任务不能覆盖较新的用户操作。
- 3D 折叠卡片仍保留带稳定 key 的空列表容器，展开后可以复用原滚动上下文；稳定 key 缺失或节点复用异常时不跨文件兜底，并输出诊断信息。

### 3.2 v1.5.74 真实验证发现的残留问题

v1.5.74 发布到 161 后，普通显隐和编辑场景可以保持列表位置，但浏览器验证发现折叠卡片时列表会暂时变为零高度，浏览器将 `scrollTop` 钳制为 `0`；展开后如果把这个瞬时值再次写入缓存，原位置仍会丢失。删除路径还存在“重绘后再清理”的时序问题：清理函数会使刚创建的延迟恢复任务失效，导致同一容器中未删除文件也可能错过恢复。

这说明仅保存一个数值并在重绘后写回不够，还必须区分稳定 key、布局是否可用以及异步任务属于哪一代状态。

### 3.3 v1.5.75 二次修复

- 为每个容器维护按 KML 稳定 ID 隔离的滚动缓存和失效版本；删除单个文件只使该文件的缓存和待恢复任务失效，不取消其他文件的延迟恢复。
- 删除前标记待失效 key，下一次捕获跳过尚未从旧 DOM 移除的节点，避免“先清理、后重绘”时又把被删除文件的旧位置读回来。
- 2D、3D 的单个/批量删除及撤销/重做路径均在 `updateKmlPanelUI` 前清理对应 key；文件重新创建时不会继承已删除文件的旧位置。
- 折叠、`display:none`、`content-visibility:hidden` 或零高度过渡期间不覆盖已有有效缓存；布局恢复后再按最近位置恢复。滚动位置缓存最多保留 512 条；失效版本表会保留当前 DOM 和待处理 key，仅对历史失效墓碑做有界淘汰，避免删除竞态重新写回旧位置。
- 增加 15 个专项回归场景，覆盖顺序变化、无稳定 ID、节点复用失败、连续 RAF、折叠/展开、零高度、CSS 隐藏、删除后同 ID 重建和删除其他文件时的并行恢复。

### 3.4 当前边界

短期修复仍保留既有字符串模板和整段替换策略，目标是先消除用户可见回顶部问题、控制发布风险，并为后续 keyed renderer 保留清晰接口。它不宣称已经完成完整的 DOM 增量更新。

## 4. 优化目标与原则

### 4.1 用户目标

1. 任何不改变当前浏览上下文的操作后，外层面板和对应 KML 内部列表滚动位置保持稳定。
2. 编辑保存后，用户仍能看到刚操作的点位或线段；必要时恢复对应行的键盘焦点。
3. 目录、文件和要素顺序变化时，位置按稳定 ID 迁移，不因索引变化恢复到错误文件。
4. 2D、3D、分享和账号同步路径具有相同的状态保持规则。

### 4.2 工程原则

- 领域状态、视图模型和 DOM 渲染分层；业务事件不得直接依赖某个具体 DOM 层级。
- 所有可交互实体使用稳定 ID，禁止以显示名称或临时索引作为状态主键。
- 默认采用增量更新；只有结构性变化或显式全量刷新才允许替换完整区域。
- 地图图层和 Cesium/Leaflet 生命周期仍由命令式适配器管理，不能为了面板框架破坏连续缩放和图层过渡。
- 不以固定数量截断文件、要素、名称或媒体入口；虚拟化必须保留准确总数和完整可达路径。
- 新增依赖必须有体积、维护、迁移和安全评估，不能为单个面板直接引入大型运行时。

## 5. 目标架构

### 5.1 Domain State（领域状态）

继续复用现有 KML 数据模型和纯函数模块，集中维护：

- 文件、目录、要素及其稳定 ID。
- `enabled`、要素显隐、展开/折叠、批量选择和编辑状态。
- 详情加载状态、错误状态、账号同步 revision 和撤销/重做历史。
- 当前视口过滤结果与完整计数。

领域状态不得保存 DOM 节点引用，也不得把 `scrollTop` 写入 KML 数据或服务端同步 payload。

### 5.2 View Model（视图模型）

新增轻量纯函数，将领域状态转换为面板渲染所需字段：

- 文件标题、权限、按钮可用性和状态标签。
- 当前应显示的要素 ID 列表、总数、加载/错误提示。
- 每个节点的 `key`、父子关系和可见性。
- 可选的 `restoreFocusKey` 与 `restoreScrollKey`。

视图模型不生成 HTML 字符串，不执行网络请求，不修改领域状态。

### 5.3 Renderer（渲染器）

按以下优先级实现：

1. 保留同 key 的文件卡片、目录和 `.kml-features-list` DOM 节点。
2. 只更新发生变化的属性、文本、按钮状态和要素行。
3. 新增节点插入，删除节点移除，顺序变化通过 keyed reorder 完成。
4. 对确需全量重建的边界，统一经过 `replaceKmlPanelContent`，自动执行滚动、焦点和选择状态恢复。

渲染器应提供可测试的 `render(previousViewModel, nextViewModel, root)` 或等价接口，避免在 2D/3D 业务事件中散落 DOM 差异代码。

### 5.4 Interaction Controller（交互控制器）

面板事件委托只负责：

1. 解析 `data-action` 和稳定 ID。
2. 调用领域命令或服务层。
3. 等待异步结果并提交一次状态变更。
4. 请求对应范围的增量渲染。

控制器不得通过“重新调用所有初始化函数”修复局部状态；初始化应幂等且与渲染生命周期分离。

### 5.5 Scheduler（刷新调度器）

把当前同步刷新和视口异步刷新统一为可合并任务：

- 同一事件循环内的多次状态变更合并为一次面板更新。
- 地图视口变化只刷新受影响文件，不重建未变化的目录和文件卡片。
- popup 关闭、详情加载和账号同步回调使用 revision/token 丢弃过期任务。
- 面板隐藏时暂停非必要的 DOM 更新，重新打开时从最新 view model 恢复。

## 6. 分阶段实施路线

### P0：问题止血（v1.5.74 首轮修复，v1.5.75 补正）

- 覆盖 2D 个人、2D 分享、3D 的外层和内部滚动状态。
- 增加旧节点销毁、新节点重建、顺序变化、无稳定 ID、折叠/展开和异步二次重绘测试。
- v1.5.74 仅作为首轮实现保留历史记录；v1.5.75 发布到 161 后完成桌面、移动端、分享模式和 3D 手工冒烟，并核对运行版本。

### P1：局部 keyed 更新（建议下一个前端迭代）

- 将目录、文件卡片和要素行增加明确的 `data-key` 契约。
- 实现不依赖第三方库的轻量 keyed child reconciler，先只覆盖 `.kml-features-list` 和文件卡片。
- 显隐操作只更新对应按钮、地图图层和要素行；名称编辑只更新对应文本及必要图标。
- 保留全量模板作为异常/结构变化回退路径。
- 增加焦点、文本输入、滚动、批量选择和拖拽状态的浏览器回归。

### P2：共享面板状态与渲染边界

- 抽取 2D/3D 共用的 KML panel view model、action 类型和状态恢复协议。
- 将网络详情加载、账号同步、地图渲染和面板渲染通过明确事件连接，消除重复的 `updateKmlPanelUI` 链路。
- 引入面板渲染性能标记：更新原因、影响文件数、DOM 新增/删除数、长任务和恢复耗时。
- 对大文件采用可见窗口渲染，但保留准确总数、按 ID 定位和键盘可达路径。

### P3：框架试点（满足决策门槛后再做）

- 只在管理后台或账号空间选择一个新建/改造页面试点，不迁移 Leaflet/Cesium 地图画布。
- 以真实页面复杂度、构建体积、交互缺陷和开发耗时为数据评估。
- 试点通过后再决定是否把 KML 面板迁移；失败可保留现有原生模块，不影响地图运行。

## 7. MVVM/MVC 与主流套件评估

### 7.1 候选方案

| 方案 | 优点 | 主要代价/风险 | 当前适配判断 |
| --- | --- | --- | --- |
| 原生 ES Modules + 自研 keyed renderer | 零运行时依赖，可渐进迁移；最贴合 Leaflet/Cesium 命令式生命周期 | 需要自行维护 diff、焦点和测试规范 | 当前短期和 P1 首选 |
| Vue 3 + Pinia | 响应式和组件模型成熟；可挂载到现有 DOM，渐进式迁移成本相对可控 | 新增运行时/构建规则；双向状态与地图命令式对象边界需要约束 | P3 首选试点候选 |
| React + Zustand/Redux | 生态最大、招聘和组件资源丰富 | JSX、React root 和状态库引入面较大；与现有原生模板和 2D/3D 生命周期混用复杂 | 可行，但不是当前最小风险方案 |
| Svelte/Svelte 5 | 编译后运行时小，组件更新粒度好 | 团队和现有代码没有使用经验；生态和调试工具迁移成本需实测 | 适合性能试点，不先全站采用 |
| Angular | DI、表单、路由和完整工程规范齐全 | 框架体量、迁移方式和学习成本明显超出当前项目需要 | 不建议 |
| 传统 MVC 自研目录 | 概念简单，可不引入依赖 | 容易退化为手写模板和控制器，不能自动解决 DOM 状态保持 | 作为分层思想保留，不单独引入套件 |

### 7.2 决策结论

当前不直接引入 Vue、React、Angular 或其他 MVVM/MVC 运行时，理由如下：

1. 本次缺陷可以通过 keyed 更新边界和滚动状态协议解决，框架不是必要条件。
2. 地图主体是 Leaflet/Cesium 命令式对象；全量迁移会把地图生命周期、面板状态和框架生命周期耦合，短期回归风险高。
3. 项目已有大量原生 ES Module、纯函数和事件委托，先建立 view model/renderer 边界可以获得框架的大部分收益，而不立即增加依赖和包体。
4. 需求文档已明确不以固定窗口静默省略内容；框架本身不能替代虚拟化、加载调度和可达性设计。

这里的 MVC 更适合作为代码组织原则，而不是再引入一套传统 MVC 套件：现有地图页已经由 Leaflet/Cesium 命令式生命周期、事件委托和 ES Module 组成，套件化 MVC 会增加控制器、模板和路由的重复边界，却不能自动保持 DOM 滚动、焦点或异步代次。短期采用“领域状态 + 纯 view model + keyed renderer + interaction controller”的轻量分层，已经覆盖 MVC/MVVM 的核心职责，同时避免新增运行时。

建议的中期方向是：原生模块继续负责地图和高频渲染；若后续连续出现多个复杂表单、目录管理、权限配置或后台页面，再以 Vue 3 + Pinia 做独立页面试点。是否推广必须由下列数据决定，而不是凭偏好决定。

### 7.3 框架引入门槛

满足至少三项并完成 P3 试点评估后，才考虑新增框架依赖：

- 未来两个迭代预计新增或大改不少于 3 个复杂页面。
- 原生组件因状态同步问题产生至少 2 个跨页面回归缺陷/迭代。
- 页面开发中超过 30% 的工作量用于手工 DOM 生命周期和重复状态恢复。
- keyed renderer 在两个真实页面中仍无法满足焦点、表单、异步竞态或可维护性要求。
- 试点构建产物首屏增加不超过 10%，交互 p95、内存和错误率不劣于原实现。

### 7.4 后续执行顺序与交付物

| 阶段 | 先决条件 | 主要交付物 | 验收闸门 |
| --- | --- | --- | --- |
| P1 keyed renderer | P0 在 161 通过 2D/3D/分享验收 | `KmlPanelViewModel`、稳定 key 契约、文件卡片与要素行 reconciler、全量回退开关 | 显隐/名称编辑仅更新目标行；焦点、滚动和拖拽回归通过；无新增未处理异常 |
| P2 状态与刷新边界 | P1 在两个真实入口稳定运行一个迭代 | 2D/3D 共用 action、revision、刷新原因和 DOM mutation 观测 | 100/1000 要素 p95 < 100ms；过期异步任务不改写当前 DOM；地图连续缩放行为不变 |
| P3 Vue 3 + Pinia 试点 | 满足至少三项框架门槛 | 仅账号空间或管理后台一个页面的独立试点、回退入口、体积/内存/缺陷对比报告 | 首屏包体增量 <=10%，交互与错误率不劣于原实现；通过评审后才讨论扩大范围 |

任何阶段都不得把 `scrollTop`、焦点或 DOM 引用写入 KML 业务模型；框架试点也不得接管 Leaflet/Cesium 地图画布的生命周期。

## 8. 功能需求

### F1. 滚动状态

- 外层 `.kml-panel-body` 与每个 `.kml-features-list` 均视为独立滚动上下文。
- 以稳定 KML 文件 ID 匹配恢复；目录或文件排序变化不得把位置恢复到另一文件。
- 文件被删除、折叠或从当前模式移除时不强行滚动到其他文件。
- 新增/展开文件没有历史位置时从顶部开始；重新展开已有文件时可恢复最近一次位置。
- 当内容高度减少导致目标位置超过最大值时，按浏览器合法范围钳制，不制造空白区域。

### F2. 焦点与编辑上下文

- 编辑保存后保留当前 KML 卡片和要素行的可见性。
- 可安全复用原节点时保留键盘焦点；节点被删除时将焦点移至同一文件的合理操作入口。
- 未提交的文本、选择和拖拽状态不得因无关文件刷新而丢失。

### F3. 刷新范围

- 点位/线段显隐只刷新对应地图图层和对应面板状态。
- 名称、描述、图标或线段属性编辑只刷新受影响要素及依赖的摘要字段。
- 目录/文件排序更新目录内顺序，但不重建未变化文件的要素列表。
- 视口变化只刷新受影响文件；详情加载只更新对应加载占位区域。
- 全量刷新必须有明确原因并通过统一 renderer 入口。

### F4. 2D/3D 一致性

- 2D 个人、2D 分享、3D 个人和 3D 分享均遵守同一稳定 ID、状态恢复和错误处理协议。
- 地图图层重绘不得改变连续缩放、popup 恢复、定位、媒体入口和线段编辑行为。
- 只读模式不能因为 renderer 复用而出现写操作入口或状态泄露。

## 9. 非功能需求与指标

在 Chrome 桌面和 390px 移动视口各建立至少一组包含 100 个以上要素的 KML fixture，记录以下指标：

| 指标 | 目标 |
| --- | --- |
| 显隐/编辑后内部列表 `scrollTop` | 与操作前相同或仅因内容减少按最大值钳制 |
| 连续两次以上异步重绘后的滚动位置 | 仍保持目标文件位置 |
| 单行名称编辑的 DOM 新增/删除数（P1 后） | 不影响其他文件；目标为 O(1) 行级更新 |
| 面板操作到可交互 | p95 < 100ms（不含用户主动等待网络） |
| 单次面板刷新长任务 | 不超过 200ms；超出必须有性能记录 |
| 1000 个要素场景 | 不静默删除名称、计数或可达入口 |
| 2D/3D 构建首屏包体 | 框架试点增加不超过基线 10%，否则不得推广 |
| 控制台错误 | 操作、异步重绘和页面切换无未处理异常 |

## 10. 测试计划

### 10.1 单元测试

- 滚动状态捕获/恢复：外层、多个内部列表、横向位置、缺失节点和内容变短。
- 稳定 ID 匹配：列表顺序变化、目录变化、重复/非法 ID 的确定性回退。
- 恢复代次：旧异步任务不能覆盖新捕获状态。
- view model：权限、显隐、展开、加载和错误状态转换。
- keyed renderer：新增、删除、移动、更新和无变化节点复用。

### 10.2 浏览器集成测试

- 2D 个人 KML：点位显隐、线段显隐、名称编辑、线段属性保存、拖拽排序。
- 2D 分享：文件/目录/要素显隐和详情懒加载后的再次渲染。
- 3D 个人与分享：同等操作、相机不跳变、面板状态保持。
- 连续操作：A→B→A、快速重复点击、popup 关闭后延迟刷新、详情加载完成后二次刷新。
- 390px、768px、1920px 视口下验证滚动条、焦点、按钮和长名称不重叠。

### 10.3 性能与观测

- 使用浏览器 Performance/Long Task、DOM mutation 计数和自定义 mark 记录刷新原因、耗时和影响节点数。
- 至少覆盖 10/100/1000/10000 个要素、1/10/50 个文件和混合点/线/面。
- 性能优化不得关闭 Leaflet 的 `zoomAnimation`、`fadeAnimation` 或 `markerZoomAnimation`。

## 11. 发布、回滚与验收

1. 每个渲染改动先补会失败的回归测试，再修改实现。
2. 发布前运行 `rtk npm run check`、相关 KML `node:test`、`rtk npm test`、`rtk npm run build` 和 `rtk git diff --check`。
3. 161 内测发布必须保留应用、数据库和模板备份；健康检查失败自动回滚到发布前版本。
4. 内测验收至少记录 2D、3D、分享和移动端滚动位置结果，以及浏览器版本和构建版本。
5. 任何 keyed renderer 或框架试点必须可通过 feature flag/页面入口回退到现有 renderer，不得阻断地图主流程。
