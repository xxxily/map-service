# 66 服务器资源安全与应用运行防护

> 状态：已实现第一阶段防护，随 v1.5.24 发布
> 依据：`github/notes/serverinfo/66_notes/reports/2026-08-19-66-server-unreachable-incident-analysis-and-service-audit.md`

## 背景

66 服务器约 1.9 GiB 内存且没有 Swap。事故报告显示，`map-service` 历史 RSS 曾达到约 839 MiB，而旧 PM2 配置允许 Node heap 达到 2 GiB、达到约 2 GiB 才重启，无法在整机失去响应前形成保护。线上瓦片缓存还积累了约 48 万个文件；旧缓存统计实现一次性读取目录并保留全部条目后排序，管理后台访问缓存面板可能造成显著内存和 I/O 峰值。

## 第一阶段目标

- 单个 Node 进程必须为 Caddy、PM2、数据库和内核保留明确内存余量。
- 生产环境不因代码文件变化自动重启，不由应用自行拉取代码，避免发布过程产生混合版本和重复重启。
- 缓存统计在大目录下保持有界内存，不因展示最近 100 条记录而保留全部缓存元数据。
- 统计重扫具备最小间隔，缓存高流量下不能每次后台刷新都触发全目录扫描。
- 统计和 PM2 配置必须有自动化回归校验。

## 实现约束

### PM2 运行边界

- 使用 `pm2.config.cjs`，兼容项目 ESM 模式下的 PM2 冷启动和恢复。
- `watch=false`，移除每日定时强制重启；代码更新只允许通过发布脚本完成。
- `--max-old-space-size=640`，`max_memory_restart=768M`。阈值是第一阶段保守值，后续必须以压测和线上 RSS 观测为依据调整，不得恢复到接近整机内存的数值。
- 发布脚本在停止前从现有 PM2 进程安全保存环境变量（临时文件 `0600`，不输出内容），再根据仓库配置生成临时配置并删除/重建应用；不会让 SSH shell 环境覆盖生产密码、Token 或代理配置。启动后校验实际进程参数，并在失败时使用同一份环境和安全阈值回滚。
- 发布前检查 `MemAvailable >= 384 MiB`、目标磁盘可用空间 `>= 2 GiB`；成功后执行 `pm2 save`，保证重启恢复仍使用安全配置。

### 代码更新边界

- `autoPullProjectCode` 默认不加载；只有显式设置 `MAP_SERVICE_ENABLE_AUTO_PULL=true` 才允许本地维护场景启用。
- 生产部署、依赖安装、构建和进程重载由 `deploy-66.sh` 统一完成。

### 缓存统计边界

- 使用 `fs.opendir` 异步迭代目录，不使用一次性 `readdir` 保存大目录条目。
- 统计只保留按更新时间排序的最近 100 条预览项，完整文件数量和字节数仍逐项累计。
- 统计扫描每 128 个文件让出事件循环；目录使用 `fs.opendir` 流式迭代。缓存 sidecar 已有合法 `size`、`updatedAt` 时直接复用，仅对旧格式或字段缺失的条目执行 `stat`。扫描期间的新增/删除通过 generation 标记，不会把新变更错误清成已同步。
- 统计重扫默认至少间隔 6 小时；快照过期或首次访问仍可立即生成，冷却期内返回旧快照并标记 `refreshing`，由 unref 定时器在冷却结束后补做一次刷新。
- 缓存正文和元数据继续使用文件流；本次不删除用户缓存、不裁剪 KML 或媒体内容。

## 验收

- `npm run check`、`npm test`、`npm run build` 通过。
- PM2 配置可由 Node 冷启动解析，生产进程不启用 watch，实际参数为 640 MiB heap / 768 MiB RSS 重启。
- 10,000 条模拟缓存统计只保留不超过 100 条预览项；125 条 sidecar 样本保持完整文件数和字节数；大目录遍历使用流式目录迭代，完整元数据不触发逐文件 `stat`。
- 部署后检查主机 `free -h`、Swap、PM2 RSS、重启次数、健康接口和日志；若健康检查或保护参数不符合预期，自动回滚。

## 后续治理

- 评估为 66 增加受控 Swap 或升级内存；Swap 仅用于削峰，不能替代应用内存治理。
- 为缓存增加容量/保留策略和低优先级过期清理，避免 11 GiB 缓存继续无界增长。
- 继续处理 SSH 预认证、失效 Caddy 路由和日志轮转等主机级风险。
