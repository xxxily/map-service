# KML 协调色板与个人空间批量移动需求

> 状态：已实现，待发布验收
> 更新时间：2026-09-01
> 关联文档：[KML 目录管理、文件排序与点位聚合](./kml-directory-ordering-and-share-point-clustering.md)、[用户系统 RBAC 与多 KML 分享](./user-system-rbac-and-multi-kml-sharing.md)

## 1. 背景与目标

当前 KML 主题色只提供一组散乱的预设色。用户为多份 KML 逐个选色时缺少成套参考，容易出现互相冲突、地图观感突兀的问题。个人空间“我的 KML”虽然已经支持跨目录多选，但移动目录仍只能逐个文件操作。

本需求建立两项一致能力：

1. 为所有 KML 主题色入口提供四组经过搭配的协调色板，同时保留任意合法 Hex 颜色输入。
2. 在个人空间对跨目录选择的 active KML 执行一次原子批量移动；已位于目标目录的文件自动跳过，不阻止其余文件移动。

## 2. 范围与边界

### 2.1 本期范围

- 2D、3D KML 数据管理面板共用四组色板。
- 个人空间“编辑 KML 信息”使用同一色板数据和颜色选择交互。
- 个人空间“我的 KML”批量操作区增加“批量移动”。
- 批量移动支持从多个目录和未分类中同时选择文件，目标可以是任一当前用户目录或未分类。
- 后端提供单次原子接口，统一完成权限、状态、目标目录、顺序和写入校验。
- 同步更新自动化测试、API 文档和变更记录。

### 2.2 不在本期范围

- 不支持跨账号移动 KML。
- 不移动回收站文件，不修改回收站原目录记录。
- 不改变分享快照中的目录名称、文件顺序和已发布内容；移动后仍按现有 revision 规则显示待同步状态。
- 不移除自定义 Hex 输入和浏览器原生取色能力，不强制历史颜色映射到预设色板。
- 不把批量移动拆成前端逐项调用单文件接口，避免部分成功和重复重排。

## 3. 协调色板

### 3.1 共享数据源

色板必须由一个共享常量定义，2D、3D 和个人空间不得维护各自副本。每组包含 8 个可直接用于地图点、线、面主题的颜色：

| 色板 | 使用倾向 | 色值 |
| --- | --- | --- |
| 森野地貌 | 山地、徒步、自然资源 | `#0f766e` `#15803d` `#4d7c0f` `#a16207` `#c2410c` `#9a3412` `#475569` `#0e7490` |
| 海岸晴空 | 水域、骑行、清爽路线 | `#075985` `#0369a1` `#0284c7` `#0891b2` `#0d9488` `#2563eb` `#4f46e5` `#6d28d9` |
| 暖霞人文 | 城市、人文、活动线路 | `#9f1239` `#be123c` `#dc2626` `#ea580c` `#d97706` `#ca8a04` `#a21caf` `#7c2d12` |
| 均衡分类 | 多类型文件的高辨识分类 | `#1b9e77` `#d95f02` `#7570b3` `#e7298a` `#66a61e` `#e6ab02` `#a6761d` `#4b5563` |

### 3.2 交互与兼容

- 色板下拉按组显示组名和色块，不使用一条无语义的颜色列表。
- 当前颜色命中预设色时显示明确选中态；自定义色不命中时仍正确显示在触发色块、Hex 输入和原生取色器中。
- 色块必须可点击并具备按钮语义、颜色值提示和键盘焦点样式。
- 继续只接受 `#RRGGBB`，提交沿用后端小写归一化规则。
- 颜色下拉使用固定尺寸和视口内定位，不得被地图面板或编辑弹窗裁切；窄屏不得横向溢出。

## 4. 个人空间批量移动

### 4.1 选择与目标目录

- 复用现有 `state.kml.selected`，允许用户在不同目录分别勾选后统一操作。
- “批量移动”仅在用户具备 `kml.own.write` 且当前不是回收站视图时显示；无选择时禁用。
- 目标目录选择器包含所有实体目录和“未分类”，即使目标目录也是部分所选文件的当前目录也允许提交。
- 客户端按当前列表的稳定显示顺序生成 `ids`，不按勾选先后随机排序。

### 4.2 服务端行为

新增接口：

```http
POST /api/v1/kml/files/batch-move
```

请求：

```json
{
  "ids": ["kml_a", "kml_b", "kml_c"],
  "directoryId": "target-directory-id"
}
```

`directoryId = null` 表示移动到未分类。

响应：

```json
{
  "directoryId": "target-directory-id",
  "movedIds": ["kml_a", "kml_c"],
  "skippedIds": ["kml_b"],
  "movedCount": 2,
  "skippedCount": 1,
  "documents": [],
  "affectedDocuments": []
}
```

契约规则：

- `ids` 必须是非空、无重复的字符串数组。
- 所有 ID 必须属于当前用户且状态为 `active`；不存在、越权、回收站文件或无效目标目录会使整个请求失败。
- 验证、源目录重排、目标目录追加和 revision 更新在同一数据库事务内完成，失败不得产生部分移动。
- 已在目标目录的文件进入 `skippedIds`，目录、位置、更新时间和 revision 均保持不变。
- 其余文件按请求 `ids` 顺序追加到目标目录末尾。
- 每个受影响源目录移除文件后重新连续编号；仅实际发生目录或位置变化的文档增加 revision。
- `documents` 返回实际移动的所选文档，按 `movedIds` 顺序排列；`affectedDocuments` 返回移动和重排导致 revision 变化的全部文档。

### 4.3 完成反馈

- 成功后从选择集合中清除 `movedIds` 和 `skippedIds`，重新加载 KML 和目录数据。
- 提示分别给出移动数和同目录跳过数，例如“已移动 12 个，跳过 3 个已在目标目录的文件”。
- 请求失败时保留当前选择，显示服务端可操作错误，不静默降级为逐项移动。
- 全部文件都在目标目录时按成功处理，提示移动 0 个、跳过全部文件。

## 5. 安全与性能

- 路由仍要求登录、CSRF 校验和 `kml.own.write` 权限。
- 服务端只查询和修改当前用户数据；其他账号的 ID 对外按资源不存在处理。
- 实现对文件数和受影响目录数保持线性复杂度，不能为每个文件重复完整扫描所有目录。
- 一次请求只重排真正受影响的源目录和目标目录，跳过项不触发写入。
- 不返回 KML 要素正文、Token、密码或其他敏感字段。

## 6. 验收标准

1. 2D、3D 和个人空间均显示四组、每组 8 个相同颜色；选择后主题色正确保存和渲染，自定义 Hex 仍可使用。
2. 色板当前值、hover、focus 和选中态清楚，桌面与窄屏下拉均不被裁切或溢出。
3. 用户可跨两个以上目录勾选 KML，一次移动到实体目录或未分类。
4. 所选文件中已有目标目录项时，该项自动跳过，其余文件正常移动；全部同目录时也不会报错。
5. 移动项按列表/请求顺序追加，所有源目录位置连续，跳过项 revision 不变。
6. 任一文件不存在、越权、在回收站或写入中途失败时，所有文件目录、位置和 revision 保持原状。
7. API 鉴权、请求响应、服务事务和前端入口均有自动化测试。
8. `npm run check`、`npm test`、`npm run build` 和 `git diff --check` 通过。
