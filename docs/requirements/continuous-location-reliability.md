# 持续定位长期运行可靠性需求

## 状态

- 状态：已实施，待发布
- 建立日期：2026-07-10
- 适用范围：前台 2D 地图、3D 地图、PWA/移动浏览器持续定位

## 背景和目标

持续定位用于长途驾驶、骑行、徒步和旅行轨迹记录。现有实现存在“界面仍显示持续定位运行中，但位置已经永久停止更新”的严重问题，手动停止并重新开启后才能恢复。

本需求要求持续定位从简单定时轮询升级为有明确状态、健康检测、自动恢复和资源上限的长期运行能力。核心目标是：临时定位失败、浏览器生命周期变化或单个异常坐标不得把整个定位会话永久锁死；用户主动停止后又不得被恢复逻辑擅自重新开启。

## 用户和场景

- 长途驾驶或乘坐高铁时，以较高速度连续移动数小时。
- 经过隧道、地下停车场、山区等 GPS 临时不可用区域后继续行程。
- 移动浏览器短暂进入后台、锁屏、BFCache 或被冻结后回到前台。
- 系统定位权限、GPS 开关、网络状态临时变化后恢复。
- 以 1—60 秒间隔记录长轨迹，并将轨迹持续保存为本地 KML。

## 范围

### 范围内

- 2D/3D 共用的持续定位状态机。
- 浏览器连续定位源、单飞轮询降级、定位源静默检测与自动重建。
- 动态漂移判断、乱序保护、候选点确认与重新定基准。
- 权限、页面生命周期、网络恢复和 Wake Lock 的健壮处理。
- 实际健康状态、最后更新时间和恢复状态展示。
- 长途轨迹的渲染、内存和 KML 持久化保护。
- 自动化长跑、错误、生命周期和竞态测试。

### 范围外

- 原生 iOS/Android 后台定位服务。
- 页面被操作系统杀死后仍在后台执行 JavaScript。
- 服务端轨迹同步、多人位置共享和导航路线规划。
- 以任意 URL 作为定位或轨迹上传目标。

## 平台能力边界

Screen Wake Lock、音频/视频保活和浏览器地理定位均受浏览器、系统省电策略与用户权限限制。Web/PWA 只能在平台允许时尽力维持后台执行，不能承诺系统锁屏、冻结或杀页后仍持续采集。

因此产品保证分为两层：

1. 页面可执行期间，定位源应持续健康运行并自动处理临时错误。
2. 页面恢复执行时，应立即识别数据是否陈旧、重建定位源并自动继续，而不是保持假运行状态。

如未来需要系统杀页后仍不中断的强保证，应建设原生前台服务/后台定位能力，不以 Web 保活技巧替代。

## 状态模型

持续定位必须区分用户意图与实际健康状态：

| 字段 | 含义 |
| --- | --- |
| `desiredActive` | 用户是否要求持续定位继续运行 |
| `phase` | `idle`、`starting`、`tracking`、`stale`、`recovering`、`suspended`、`permission-blocked`、`unsupported` |
| `generation` | 当前会话/恢复代次，用于拒绝旧回调 |
| `lastSignalAt` | 定位 provider 最近一次回调时间，静止不改变坐标也应刷新 |
| `lastFixAt` | 最近一次有效位置被消费的时间 |
| `lastProviderTimestamp` | 最近已接受的 provider 原始时间戳，用于拒绝乱序数据 |
| `consecutiveTimestampAnomalies` | 连续时间戳回退或重复缓存位置次数，达到阈值后重建定位源 |
| `consecutiveFailures` | 连续失败次数 |
| `restartCount` | 自动重建定位源次数 |
| `lastError` | 最近错误的对外安全摘要 |
| `permissionState` | `granted`、`prompt`、`denied` 或 `unknown` |

界面不得只根据 `desiredActive=true` 显示“健康跟踪中”。`recovering`、`stale` 和 `permission-blocked` 必须有明确文案，并展示最后一次成功更新时间。

## 功能需求

### R1. 单一连续定位源

- 支持时应使用浏览器 `watchPosition` 作为连续采集主路径。
- watcher 不可用时可降级为 `getCurrentPosition` 单飞轮询；下一轮只能在上一轮完成或超时后开始。
- 任意时刻只能存在一个有效 watcher、一个 watchdog 和一个恢复/轮询定时器。
- 配置的“定位时间间隔”用于限制地图/KML 消费频率；provider 高频回调时保留最新位置，不堆积渲染任务。
- 地图/KML 消费任务必须有应用层 deadline；一次消费者 Promise 永久悬挂时应中止旧 generation 并自动恢复。

### R2. 会话和乱序保护

- 每次启动、停止、暂停和定位源重建都应更新 generation。
- success、error、超时、权限回调和异步渲染在写状态前必须校验 generation。
- provider timestamp 早于最近已处理 timestamp 的数据应丢弃。
- 少量乱序不得造成重建风暴；连续回退或“相同 timestamp + 相同坐标”的缓存位置达到阈值后必须主动重建，新的 generation 重新建立时间戳水位线。
- timestamp 相同但坐标确有推进的两个独立样本仍可用于确认漂移重锚，避免秒级时间戳把合法移动永久锁死。
- 用户停止后，迟到回调、生命周期事件和权限变化不得重新开启定位。

### R3. watchdog 与错误恢复

- 长时间没有任何 provider 回调时进入 `stale`，清理旧源并自动重建。
- `POSITION_UNAVAILABLE`、`TIMEOUT` 和同步异常进入指数退避恢复，退避必须有上限。
- `PERMISSION_DENIED` 进入 `permission-blocked`，停止高频重试；权限恢复或页面重新可见后再进行一次恢复检查。
- 消费者（地图渲染、KML、本地存储）一次失败不得销毁定位 watcher，后续位置仍应继续处理。
- 消费者长时间不返回时不得继续伪装为健康 tracking，应超时、撤销旧任务并重建定位源。

### R4. 生命周期恢复

- 监听 `visibilitychange`、`pageshow`、`pagehide`、`freeze`、`resume`、`focus` 和 `online`。
- `pagehide`/`freeze` 应标记暂停并使当前回调失效。
- 回到可见、`pageshow` 或 `resume` 时合并事件风暴，只执行一次健康检查/定位源重建。
- 恢复后的首批位置不得因仍引用暂停前的旧位置而永久拒绝。
- 系统时间/NTP 回拨不得把消费节流、watchdog 或 KML 检查点延后到旧时间追平之后。

### R5. 单次定位 deadline 与坐标契约

- 普通单次定位、持续 `watchPosition` 和 watchdog 轮询必须统一使用浏览器 Geolocation，原始坐标明确按 WGS-84 处理。
- WGS-84 坐标只允许在进入高德底图渲染前由项目代码转换一次为 GCJ-02；`coordType` 必须描述实际坐标基准，不得只按 provider 名称推断。
- 高德 JSAPI 定位结果的 SDK 转换状态和 IP 粗定位不得静默混入精确当前位置或轨迹；浏览器定位失败时应明确返回失败，不使用坐标基准不明的结果兜底。
- 浏览器单次定位必须有独立于底层 API 的应用层硬超时，不能只相信原生 `timeout` 参数。
- 浏览器错误 code、原始 timestamp 和精度应被保留到标准位置对象。

### R6. 漂移判断和重新定基准

- 不得使用固定距离阈值作为唯一判断依据。
- 合理移动上限必须结合前后采样时间差、定位精度和最大合理速度，至少覆盖 500 km/h 的高铁场景。
- 一个超大跳点只进入候选态；下一独立位置若与候选点空间一致，应确认真实位置并重新定基准。
- 单个异常点被拒绝后，后续正常点必须仍有机会被接受，禁止永久拿旧锚点拒绝所有新位置。
- 静止样本虽然不新增轨迹点，也必须刷新漂移过滤所使用的最后接受坐标、精度和时间戳，停留起始时间单独保留。
- 隧道、生命周期暂停或长时间无信号恢复后允许重新定基准，并保留轨迹时间缺口。

### R7. 长途资源和持久化保护

- 完整轨迹数据与屏幕历史标记分离；屏幕同时渲染的历史点必须有固定上限。
- 实时轨迹 KML 的存储数据保持完整；地图最多渲染最近 120 个 Point，轨迹线显示顶点总量限制为约 2000，导出仍使用完整坐标。
- “仅路线”开启时，实时 KML 只能生成轨迹 LineString，不生成每个位置的 Point。
- 中途关闭再开启轨迹记录时继续使用当前会话 KML，但按多个 LineString 分段保存，停录期间的位置不得被记录或用直线跨接。
- KML 更新不得遗留上一轮 feature/layer/entity 索引。
- 定位采集、地图渲染和 KML 保存必须错误隔离。
- KML 保存先完成存储事务再替换渲染内容，失败时回滚内存 features 并保留旧图层。
- 本地存储失败应指数退避，不得每个定位点重复全量序列化；停止会话时仍应尝试最终落盘并明确提示失败。
- localStorage 被禁用或读取抛错时，地图和定位模块仍应启动；KML 可退化为当前页面内存模式。

### R8. 保活资源

- Wake Lock 获取、释放和重新获取必须幂等。
- 用户在 Wake Lock 请求完成前停止时，新得到的 sentinel 必须立即释放。
- sentinel 被系统释放且定位仍处于期望运行、页面可见时可重新申请。
- 音频/视频降级资源只创建一次，停止后必须暂停，不得持续占用资源。

### R9. 热配置和交互

- 热编辑间隔、缩放、历史点上限、轨迹记录方式和自动旋转时，不得由入口文件自行创建定时器。
- 热编辑必须调用统一控制器配置接口，且不得重复创建 watcher。
- 定位管理对话框至少展示：实际状态、最后更新时间、连续失败数、记录间隔和轨迹记录模式。
- 定位按钮必须以可见徽标展示 tracking、recovering、stale、suspended、permission-blocked 等实际状态，不能只写入 title/aria 属性。
- 定位间隔只接受 1—60 秒整数；缩放和历史点上限必须严格校验，拒绝部分数字、小数和超大定时器值。

## 安全和隐私

- 位置信息仅按现有本地轨迹规则处理，本次不新增网络上传。
- 日志和错误文案不得输出访问 Token、敏感请求头或其他服务端配置。
- 页面使用 `Referrer-Policy: no-referrer`，访问日志中的 `coords` 查询参数必须脱敏，避免行程坐标进入 Referer 或 access.log。
- 不新增任意 URL 代理或外部回调入口。

## 验收标准

1. 15 秒间隔、100 km/h 连续移动 8 小时的虚拟测试中，位置持续被接受且资源数量不增长。
2. 15 秒间隔、500 km/h 以内移动不因固定距离阈值永久锁死。
3. 单个远距离异常点被拒绝；两个相互接近的新位置可确认重锚并恢复。
4. watcher 静默超过阈值后自动清理和重建，最终只有一个 watcher。
5. 临时错误自动退避恢复；权限拒绝不高频重试，权限恢复后自动继续。
6. stop 后推进虚拟时钟、触发生命周期/权限事件和旧回调均不会复活定位。
7. 同一浏览器 WGS-84 样本经单次定位、持续 watcher 和 watchdog 轮询得到完全一致的 GCJ-02 地图落点；浏览器失败时不会切换到坐标基准不明的高德/IP 位置。
8. 异常未来 timestamp、系统时钟回拨、重复缓存位置和永久悬挂消费者均可自动恢复。
9. 默认仅路线模式不会生成离散 KML Point；非精简模式也只渲染固定数量的点和抽稀轨迹线。
10. 暂停/继续录制保留同一 KML 的前段数据、排除停录区间，并在保存失败时退避及向用户告警。
11. 2D/3D 共用控制器契约，相关 `node:test` 全部通过。
12. `npm run check`、`npm test`、`npm run build` 全部通过。

## 后续路线

- 将长期轨迹从同步 localStorage 迁移到 IndexedDB 或服务端增量存储。
- 将存储空间告警从保存失败提示升级为主动容量预警。
- 如需锁屏和系统杀页后仍持续定位，评估 Capacitor/原生 App 的后台定位服务。
