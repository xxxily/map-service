# 管理后台数值配置自由裁量与 KML 移动端布局修订需求

状态：实现完成（2026-08-27，v1.5.50）

## 1. 背景与目标

管理后台“用户体系设置”历史上在前端 `max` 属性和服务端归一化逻辑中同时写入了多组业务最大值，例如单个分享最多 20 个 KML、会话最长 30/90 天、聚合阈值最多 1000、配额和空间范围固定封顶。管理员无法根据实际部署容量和业务规模调整策略。

同时，移动端 KML 目录行的名称、数量徽标和右侧图标曾因 flex 换行、行高和按钮高度不同而出现垂直错位；回收站返回按钮文案也过长。

本次修订目标：

- 管理员可自由设置业务策略数值，不再受任意固定最大值限制。
- 只保留真实技术硬边界、数据类型边界和字段间必要关系。
- 地图面板与账号页的目录名称、数量、按钮在常见移动端宽度保持同一水平中心线。
- 回收站入口返回按钮只显示“返回”，完整含义放在 `title` 中。

## 2. 数值配置规则

### 2.1 不设置固定业务最大值

以下管理项只校验正数、非负数或正整数，不再设置代码级固定最大值：

- 会话有效期、记住登录有效期和高风险操作再验证窗口。
- KML 文件数、单文件要素数、用户总要素数和回收站保留天数。
- 单个分享最多 KML 数、分享密码授权有效期。
- 强制聚合最少点位数。
- 分享限流统计窗口、瓦片请求数、清单请求数和内存访客条目数。
- 空间边界余量、最大面积和最大对角线。

默认值只是新部署或缺省配置的初始建议，不是不可逾越的上限。

### 2.2 保留的硬边界

- 地图缩放级别仍为 `0～24`，由当前地图引擎和产品缩放模型决定。
- 分享所有者可编辑的聚合算法参数继续使用既有技术范围：`gridSize` 24～128、`minClusterPoints` 2～1000、`maxMembersPerCluster` 100～20000；管理员强制聚合阈值 `share.kmlClusterMinPoints` 不受分享级 1000 上限限制。
- 单文件 KML 大小不得超过部署级 multipart 运输层限制。默认 `50 MiB`，可通过 `MAP_SERVICE_KML_IMPORT_MAX_BYTES` 调整。
- KML 编辑、同步和迁移 JSON 请求默认取 `64 MiB` 与 multipart 上限 `1.25` 倍中的较大值；可通过 `MAP_SERVICE_KML_JSON_MAX_BYTES` 调整。
- 整数必须是 JavaScript 安全整数；空间数值必须是有限数，避免溢出、`NaN` 和无穷值进入持久化配置。
- 密码、用户名、显示名称、脚本和 URL 等安全长度限制不属于管理员资源配额，不在本次放开范围内。

### 2.3 必要关系校验

- 记住登录有效期不得短于普通会话有效期。
- 用户总要素数不得小于单文件要素数；系统默认配额和个人配额覆盖使用同一规则。
- 不限授权最大面积和最大对角线不得大于空间限制总体阈值。
- 个人配额留空时继承系统默认；填写后按合并后的有效配额执行运输层和关系校验。

### 2.4 历史配置兼容

- 旧数据库中的系统配额和个人覆盖在读取时只保留已知的正安全整数字段，未知字段和非法值忽略。
- 历史单文件大小超过当前 multipart 运输层上限时，读取结果收敛到当前上限；历史“用户总要素数小于单文件要素数”时，下调单文件要素数以满足关系。
- 读取归一化不主动改写数据库；管理员再次提交配额时仍执行严格校验，普通资料编辑不会因旧版本遗留配额而失败。

## 3. 前后端契约

- `/api/v1/auth/config` 返回 `share.maxFilesPerShare` 和 `kml.importTransportMaxBytes`，账号端创建/编辑分享和导入 KML 使用服务端值，不再写死 `20` 或 `10 MiB`。
- 管理设置和用户列表响应返回 `technicalLimits`：

```json
{
  "kmlImportTransportMaxBytes": 52428800,
  "kmlJsonTransportMaxBytes": 67108864
}
```

- multipart 超限返回 `413 KML_IMPORT_TRANSPORT_LIMIT_EXCEEDED`。
- KML JSON 请求超限返回 `413 KML_JSON_TRANSPORT_LIMIT_EXCEEDED`；普通 JSON 请求仍使用较小的全站限制并返回 `REQUEST_BODY_TOO_LARGE`。
- 前端仅为技术硬边界和动态关系渲染 `max`；其他业务数值字段不得重新加入固定 `max`。

## 4. KML 移动端布局

- 目录标题采用两列网格：左侧名称/数量，右侧操作区。
- 名称区内部采用“拖动标记、可省略名称、固定数量徽标”三列网格。
- 名称区、数量徽标、操作区和图标按钮使用相同垂直中心；长名称只省略，不覆盖或挤出操作按钮。
- 地图面板和账号页均覆盖 `320px`、`375px`、`390px` 宽度；横向溢出必须为 `0`。
- 回收站返回按钮显示“返回”，并保留 `title="返回使用中的 KML"`。

## 5. 验收标准

1. 后台可保存超过旧最大值的会话、配额、分享数量、聚合阈值、限流和空间策略数值。
2. 单个分享配置为大于 20 后，账号端可选择并创建超过 20 个 KML 的分享。
3. 超过 multipart/JSON 运输层限制时返回稳定的 `413` 错误码，不出现通用保存失败。
4. 系统默认配额或个人覆盖中“总要素数小于单文件要素数”时返回 `400 VALIDATION_FAILED`。
5. 历史超运输层配额、关系冲突和未知字段在读取时安全收敛，且不会阻断仅修改显示名称等普通资料操作。
6. `320/375/390px` 下目录名称、数量和图标中心线一致，且没有横向溢出。
7. 完成 `npm run check`、`npm test`、`npm run build` 和相关浏览器实测。
