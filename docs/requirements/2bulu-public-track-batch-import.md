# 两步路用户公开轨迹列表批量导入需求

> 状态：第一版实现中
> 更新时间：2026-09-01
> 关联文档：[两步路授权浏览器助手与浏览器内导入](./2bulu-authorized-browser-helper.md)、[两步路公开分享轨迹导入](./2bulu-public-track-import.md)、[用户体系 API](../api-user-system.md)、[两步路导入助手用户操作手册](../user-guides/two-bulu-import.md)

## 1. 背景与目标

当前浏览器助手只能对单个两步路公开轨迹分享链接执行读取和导入。两步路用户空间的“我的轨迹”列表页已经聚合了同一用户的公开线路，用户希望按列表顺序或筛选条件批量导入，减少逐条复制链接、重复等待页面加载和手工整理目录的成本。

本需求新增“用户公开轨迹列表批量导入”能力：用户输入两步路公开用户轨迹列表 URL，助手在用户自己的浏览器会话中读取页面已经展示的公开轨迹项及其公开统计信息，按筛选/排序结果逐条复用现有单轨迹导入链路，并将结果放入以两步路用户昵称命名的专属 KML 目录。

## 2. 范围与原则

### 2.1 范围内

- 支持 `https://www.2bulu.com/spaceindex/my_track.htm?userId=...` 形式的公开用户轨迹列表页；兼容 `2bulu.com`、`www.2bulu.com`、`app.2bulu.com` 同主机变体。
- 读取列表页可见的公开轨迹链接、轨迹名称、点位数量、发布时间、轨迹里程、点赞数量、收藏数量和用户昵称（字段缺失时保留空值并允许继续筛选）。
- 支持按原列表顺序或发布时间、里程、点赞数、收藏数、点位数排序，并支持上述数值/日期的最小值和最大值筛选。
- 批量导入前展示匹配数量和每项摘要；用户确认后按顺序逐条导入。
- 自动创建或复用当前账号下与用户昵称同名的 KML 目录；批量导入的文件通过现有 `directoryId` 归属到该目录。
- 单项失败可跳过并继续后续项；批量结束返回成功、跳过、失败和未处理统计，以及每项错误摘要。
- 每个轨迹项继续使用现有浏览器助手单轨迹读取、服务端 KML 校验、权限、配额、审计和幂等规则。

### 2.2 范围外

- 不新增服务端任意 URL 抓取或列表爬虫接口，不在服务端代持两步路 Cookie。
- 不绕过登录、验证码、WAF、频率限制或动态签名；列表页需要用户自行完成的验证由浏览器页面承担。
- 不承诺读取未渲染、分页未展开、私密/删除或非公开轨迹；无法从当前页面确认的字段不得猜测。
- 不做定时同步、差异同步、后台队列或跨用户共享目录。
- 不静默截断列表。超过客户端可承受的批量条目上限时必须拒绝并提示用户缩小筛选范围。

## 3. 用户流程

1. 用户在账号中心“我的 KML”或 2D 地图 KML 面板点击“从两步路批量导入”。入口仍要求当前账号已登录、具备 `kml.own.write` 且浏览器助手在线。
2. 用户输入公开用户轨迹列表 URL，设置可选筛选和排序条件：
   - 点位数量：最小值、最大值；
   - 发布时间：起始日期、结束日期；
   - 轨迹里程（km）：最小值、最大值；
   - 点赞数量：最小值、最大值；
   - 收藏数量：最小值、最大值；
   - 排序字段：列表顺序、发布时间、里程、点赞数、收藏数、点位数；
   - 排序方向：升序或降序；
   - 数据不完整策略：必须完整或允许仅导入轨迹线；
   - 目录策略：默认按用户昵称创建/复用专属目录。
3. 助手打开或复用受管的两步路列表标签页，等待页面完成加载并提取公开轨迹项。网站显示预览：用户昵称、识别条目数、筛选后条目数和字段缺失警告。
4. 用户确认后，助手按排序结果逐条打开轨迹详情页并复用现有单条导入流程。每项使用独立且稳定的 `requestId`，响应丢失可安全重试。
5. 首次导入该用户时创建目录；若同一账号已有同名目录则复用，不覆盖目录内既有文件。目录创建遇到同名并发冲突时重新读取目录列表并复用已存在目录。
6. 批量完成后，账号中心刷新 KML 列表；地图页将成功导入文件加入当前个人图层并适配成功文件的范围。页面展示汇总和失败项，失败项不阻断已成功文件。

## 4. 列表项识别与数据契约

### 4.1 支持的链接

列表页本身只作为浏览器端输入，不提交给服务端保存 API。列表项必须解析为现有受支持的单轨迹链接：

```text
https://www.2bulu.com/track/t-<trackId>.htm
https://www.2bulu.com/track/track_detail.htm?trackId=<trackId>
https://www.2bulu.com/share/share_track.htm?trackId=<trackId>
```

助手必须使用现有 `normalizeTwoBuluShareUrl` 规范化链接，去除 fragment、额外查询参数和会话标识。无法规范化的链接从预览中标记为“不可导入”，不得交给服务端。

### 4.2 列表摘要结构

浏览器助手列表解析结果使用以下结构，字段缺失时为 `null` 或空字符串：

```json
{
  "sourceUrl": "https://www.2bulu.com/spaceindex/my_track.htm?userId=...",
  "userName": "山友阿明",
  "items": [
    {
      "url": "https://www.2bulu.com/track/track_detail.htm?trackId=...",
      "name": "白云山环线",
      "pointCount": 128,
      "publishedAt": "2026-08-20T10:30:00.000Z",
      "distanceKm": 12.34,
      "likeCount": 56,
      "favoriteCount": 12,
      "position": 0
    }
  ],
  "detectedCount": 1,
  "warnings": []
}
```

解析只能使用页面可见 DOM、公开链接属性和已展示文本；不执行列表页脚本文本，不读取 Cookie、Authorization 或非公开接口响应。字段解析失败时保留条目并在预览中标记缺失字段，只有 URL 无法识别时才排除条目。

### 4.3 筛选与排序规则

- 数值字段按非负数比较；千分位、中文单位和小数统一规范化。里程统一为 km。
- 发布时间按 ISO 日期解析；无法解析的条目在设置了日期筛选时视为不匹配，未设置日期筛选时保留并排在可解析日期之后。
- 最小值和最大值同时填写时必须满足 `min <= max`；非法输入在弹窗内阻止提交。
- 排序的次关键字固定为 `position`，再次关键字为规范化 URL，保证结果稳定。
- 过滤和排序只作用于列表预览，不改变单条轨迹详情中的真实点位/里程数据。

## 5. 批量限制、并发与错误处理

- 单次批量最多处理 200 个匹配条目；列表识别超过 200 个时不静默截断，要求用户增加筛选条件后重试。
- 导入严格按排序后的顺序串行执行，默认不并发打开多个两步路标签页，避免触发第三方风控和本地资源争用。
- 单项开始前记录批次 ID、项位置和稳定 `requestId`；成功后清理该项重试意图，失败项保留至批次结束供“重试失败项”使用。
- 可恢复错误（超时、响应丢失、临时助手不可用）最多按同一 `requestId` 重试一次；需要用户操作（登录、验证码、WAF）立即暂停批次并允许用户继续或结束。
- 单项失败后默认继续后续项；若用户选择“停止”，未开始条目标记为 `cancelled`，已成功文件不回滚。
- 目录创建失败、权限失效或配额不足属于批次级错误，停止后续导入并保留已成功文件。
- 批次不创建空 KML；单项服务端保存失败不影响其他已完成条目。

## 6. 目录归属规则

- 默认目录名称为列表页解析出的用户昵称，经过现有 KML 目录名称规范化；昵称为空时使用“ 两步路用户轨迹 ”（去除首尾空格后为“ 两步路用户轨迹 ”的规范化版本）。
- 目录名称最大长度、同名判定和目录数量上限复用现有 `createKmlDirectory` 规则。
- 每个单项保存请求增加可选 `directoryId`；服务端必须校验目录归当前用户所有，不接受跨用户目录或任意目录名称作为主键。
- 目录内文件顺序按批次导入顺序追加；重复运行同一批次使用单项 `requestId` 幂等重放，不创建副本。
- 用户可在现有 KML 管理中重命名、移动或删除该目录；批量导入不建立不可变绑定。

## 7. 接口与消息协议变更

### 7.1 浏览器助手消息

新增 `IMPORT_2BULU_BATCH` 请求和 `BATCH_PREVIEW_RESULT` 响应。请求仅包含列表 URL；筛选条件在网站拿到摘要后本地执行，避免把列表页或非公开字段发送到服务端。

```json
{
  "protocolVersion": 1,
  "type": "IMPORT_2BULU_BATCH",
  "requestId": "batch-preview-uuid",
  "url": "https://www.2bulu.com/spaceindex/my_track.htm?userId=..."
}
```

返回 `status=success` 时携带上述列表摘要；页面未加载完成、要求验证或列表结构不可识别时返回稳定中文错误码，例如 `TWO_BULU_LIST_URL_INVALID`、`TWO_BULU_LIST_DATA_NOT_RECOGNIZED`、`TWO_BULU_UPSTREAM_BLOCKED`。

### 7.2 单条保存 API

`POST /api/v1/kml/import/2bulu/browser-helper` 请求增加：

| 字段 | 规则 |
| --- | --- |
| `directoryId` | 可选；字符串 ID，必须属于当前用户，空值表示未分类；不接受目录名称 |

成功响应继续返回单条 KML 和 `importSummary`，新增的批次统计由前端根据每项结果汇总，不新增批量持久化任务。

## 8. 安全与隐私

- 服务端仍只接收规范化的单轨迹 URL、标准 KML 和受校验的 `directoryId`；不接收用户列表 URL 作为保存目标，不新增任意 URL 代理。
- 列表摘要只在浏览器助手和 map-service 当前页面内短暂传递；不上传两步路 Cookie、账号、请求头、原始列表 HTML、非公开响应或验证码内容。
- 用户昵称、轨迹名称和统计字段视为不可信文本，展示和目录写入前执行长度、控制字符和 HTML 转义处理。
- 批量预览和结果卡片不得使用原生 `alert`、`confirm` 或 `prompt`，复用项目统一 Dialog。
- 每个单项沿用现有 CSRF、权限、XML/XXE、XSS、大小、配额和审计校验；批次 ID 不作为权限凭据。

## 9. 验收标准

1. 输入示例用户列表 URL，能识别页面中所有可见且可规范化的公开轨迹链接，并显示用户昵称和识别数量。
2. 点位数量、发布时间、里程、点赞和收藏的最小/最大筛选组合结果正确；排序结果稳定且可复现。
3. 预览确认后按顺序逐条导入；任一项失败不会删除已成功文件，最终汇总准确列出成功、跳过、失败和取消数量。
4. 批量首次运行自动创建昵称目录，后续运行复用同名目录；所有成功文件的 `directoryId` 正确且目录内顺序与导入顺序一致。
5. 重放同一单项 `requestId` 不重复创建 KML、不重复占用配额；批量中断后可从失败项继续。
6. 服务端拒绝不存在、他人所有或格式非法的 `directoryId`，并保持现有敏感字段脱敏和审计行为。
7. 未登录、无写权限、助手未安装/未授权、列表页需要验证码、列表结构无法识别和超过批量上限时均有明确错误，不创建空 KML。
8. 新增纯函数、消息协议、服务端目录校验和前端批量流程均有 `node:test` 覆盖；通过 `npm run check`、`npm test` 和 `npm run build`。

## 10. 后续路线

- 若两步路提供稳定官方列表 API，可新增 provider 适配器，复用本地筛选和单项保存契约。
- 可在用户明确授权后增加“只导入新轨迹”指纹预览，但必须基于稳定轨迹 ID，不以中文标题作为主键。
- 可增加分页/加载更多的显式用户操作；在未能确认完整列表前不得宣称“全部导入”。
